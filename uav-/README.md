# 一、业务需求理解

根据现有巡视策略要求，系统需要根据**机巢坐标、杆塔坐标、任务类型**进行空间计算、时间计算和任务编排，并能够自动执行；
运行过程中，根据天气变化和实际任务完成进度进行动态调整。

现有巡视业务主要包括以下几类任务：

1. 精细化巡视：原则上每年完成一轮，并支持临时任务；
2. 通道巡视：至少每月完成1次，在机巢空闲时应尽可能提高巡视频次；
3. 红外测温：每年6—8月对耐张塔线夹完成一轮测温，并支持全年临时测温任务；
4. 仿线飞行：具备相关条件后原则上每年完成1次。

业务任务优先级为：
**临时任务 > 红外测温 > 精细化巡视 = 仿线飞行 = 通道巡视。**

同时还有一个非常重要的约束：
**精细化巡视、仿线飞行、通道巡视三类任务必须 同步推进，不能把某一种类型全部完成以后，再开始另外一种任务。**

因此，本项目本质上属于一个：
> **带空间约束、时间约束、资源约束、任务优先级约束和动态环境约束的多任务、多机巢无人机调度问题。**

第一，哪些任务需要执行？
第二，这些任务可以由哪些机巢执行？
第三，一次无人机飞行应该组合哪些杆塔？
第四，所有架次应该按照什么先后顺序执行？
第五，如果天气、任务进度或临时任务发生变化，剩余计划应该怎样重新调整？

# 二、第一步：从现有数据建立“机巢—杆塔—任务”基础模型
目前已有的数据主要包括两部分。
2.1 机巢数据：
当前调度程序只把状态为：**“已安装”**的机巢作为真正可以执行任务的机巢。
2.2 杆塔数据
当前杆塔数据包括约：17,845基杆塔、312条线路。
每基杆塔/线路包括：线路名称、电压等级、杆塔名称、经度、纬度。

因此，目前已有数据最适合先解决三个问题：
1. 杆塔距离哪些机巢比较近？
2. 某个机巢理论上需要负责哪些线路和杆塔？
3. 如何把大量杆塔按照线路空间关系组织成若干无人机飞行架次？

# 三、第二步：空间计算——先解决“谁能够执行这个任务”
任务调度的第一层不是时间，而是空间。
系统必须首先知道：
    某一基杆塔附近有哪些机巢具有潜在执行能力？
当前算法采用经纬度球面距离计算，也就是Haversine距离。对于每一基杆塔，计算其到所有已安装机巢之间的距离。
比如：某基杆塔T001：
    到机巢A：4.8 km、到机巢B：5.1 km、到机巢C：6.4 km、到机巢D：15.2 km
当前代码不会简单得到：
T001 → A然后永久固定。
而是保留距离较近的Top-3个候选机巢：
T001：
    第一候选机巢 A，4.8 km
    第二候选机巢 B，5.1 km
    第三候选机巢 C，6.4 km
这样设计的原因，是为了给后续动态调度保留调整空间。

# 四、第三步：不是只选最近机巢，而是综合“距离和负载”进行任务分配
有了多个候选机巢以后，下一步才是真正决定：当前这个任务由哪个机巢承担？
如果只按照距离最短分配，可能会出现一个非常典型的问题：
    距离某些线路最近的机巢承担大量任务，而附近其他机巢长期空闲。
因此，当前算法不是简单使用：[最近距离]，而是采用[综合计算]:
每个任务从 Top-K 候选机巢中选择：
cost = distance_km + load_penalty_km * 当前相对负载
cost = Distance_{ij}+\lambda Load_j
    是一个可解释、在线可更新的贪心基线算法。
其中：
(Distance_{ij}) 表示杆塔i到机巢j的距离；
(Load_j) 表示机巢j当前已经承担的任务负载；
(\lambda) 表示负载均衡的权重=1.5

最终选择综合cost最低的机巢
    比如：一个杆塔距离 机巢A：4.6 km、机巢B：5.0 km
    但 机巢A当前已有 300 个任务，机巢B当前只有 30 个任务
    那么算法可能自动选择B

# 五、第四步：从“单个任务”进一步组合成“无人机架次”
任务分配到机巢以后，还不能直接执行。
原因是实际无人机运行的单位不是“单个杆塔任务”，而是“一个飞行架次”。
一个“任务”可以是：
    某线路#31、执行精细化巡视
当前算法首先按照：机巢+线路+任务类型 对任务进行分组。
随后在线路内部按照杆塔号排序：
#31#32#33#34
然后从第一基杆塔开始，不断尝试把下一基杆塔加入当前架次。

每加入一基杆塔，就重新计算整个架次：

总飞行距离；
飞行时间；
杆塔作业时间；
是否超过最大架次能力。

如果没有超过，则继续增加杆塔。
如果超过，则结束当前架次，并从下一基杆塔开始生成新的架次。
这样就把大量独立任务自动转换成可以真正被无人机执行的飞行计划。

# 六、第五步：时间计算——判断一个架次到底能不能完成
形成候选架次之后，系统必须回答：这次飞行需要多长时间？
当前版本将总时间拆成两部分：[T_{flight}+T_{service}]

第一部分是飞行时间。
    假设架次路线为：机巢→ T1→ T2→ T3→ 机巢
    那么总航程为：[D=D(N,T_1)+D(T_1,T_2)+D(T_2,T_3)+D(T_3,N)]
第二部分是任务作业时间。
    不同任务的作业方式不同，所以作业时间也应该不同。
因此当前为不同任务类型预留了不同的单塔服务时间,[service_minutes]
例如假设无人机最大允许架次时间为45分钟，预留8分钟安全时间，则真正允许调度的最长任务时间为：[45-8=37分钟]
因此一个预计40分钟的架次虽然理论上低于45分钟，但仍然不会被安排。
这体现的是：调度系统不能把无人机性能完全“吃满”，必须留出返航和异常处理余量。


# 七、第六步：完成空间和时间计算以后，才进入真正的“任务编排”
前面的计算解决了：谁可以执行；一次飞哪些杆塔；预计需要多少时间。
接下来才是整个系统最核心的业务问题：
    这么多可以执行的架次，到底先执行哪个？
当前算法首先按照甲方要求建立基础优先级：
临时任务 > 红外测温 > 精细化巡视 = 仿线飞行 = 通道巡视
可以用简单分数表达：[BASE_PRIORITY]
    这里的400、300、200不是业务中的真实分值，而是算法内部表示优先层级的方法。

此外，为什么“三类同级任务”不能只设置相同优先级？这是整个算法最关键的一点之一。
甲方不仅要求：精细化 = 仿线 = 通道，还明确要求：三类任务必须同步开展。
如果程序只是简单把三者都设为200分，仍然不能保证同步推进。
比如：
当前三类任务完成率为：
    精细化巡视：70%、通道巡视：65%、仿线飞行：20%
如果只看基础优先级：200，那么系统认为 通道巡视快，路线也短，就会继续选择通道巡视，最终可能会：精细化巡视：90%、通道巡视：95%、仿线飞行：25%
当前算法又增加了一层：任务进度公平性机制。

同步推进的核心：谁进度落后，就动态提高谁的调度权重

当前算法会实时计算三类任务完成进度。

还是以上述数据为例：

精细化巡视：70%
通道巡视：65%
仿线飞行：20%

当前最高进度是70%。

那么可以认为：

精细化进度赤字：0%
通道进度赤字：5%
仿线进度赤字：50%

系统按照：

W\times ProgressDeficit
]

为进度落后的任务增加调度分数。




# 三、当前算法总体技术思路

当前Python代码采用的总体思路可以概括为：

**基础数据 → 空间计算 → 候选机巢 → 任务生成 → 机巢分配 → 架次生成 → 时间计算 → 任务排序 → 日计划生成。**

整体流程如下：

```text
机巢坐标
    │
    ├────────────┐
    │            │
    ↓            ↓
筛选已安装机巢   杆塔坐标
    │            │
    └──────┬─────┘
           ↓
      空间距离计算
           ↓
 每基杆塔寻找Top-K候选机巢
           ↓
   距离+负载综合分配
           ↓
        生成任务
           ↓
     按线路恢复塔序
           ↓
   组合连续杆塔形成架次
           ↓
     计算架次总航程
           ↓
   计算预计飞行/作业时间
           ↓
   判断是否超过架次限制
           ↓
  任务优先级+同步推进评分
           ↓
     生成日级执行计划
```

当前版本主要解决的是：

> **“一个静态任务池在当前资源条件下应该怎么分配和排序。”**

天气动态调整、临时任务实时插队、任务执行状态反馈之后的滚动重排，是在当前算法框架之上进一步增加的功能。

# 六、为什么精细、仿线、通道都设置为200分

这是非常值得向老师和专工重点解释的一点。

如果代码写成：

```text
精细巡视 = 220
仿线飞行 = 210
通道巡视 = 200
```

那么调度器长期运行以后，很可能会出现：

> 精细化任务始终比另外两类任务优先。

这样就违反了甲方提出的：

> 三类任务必须同步开展。

所以当前设计首先让三种任务的：

**基础优先级完全相同。**

即：

$$
P_{detail}
==========

# P_{line}

P_{channel}
$$

之后再根据：

* 哪一类完成进度落后；
* 哪一个架次效率更高；

动态调整实际调度分数。

因此，“相同优先级”不是意味着系统随机选择，而是意味着：

> **先保证业务等级平等，再根据实时进度进行动态平衡。**

# 十二、第四部分：空间距离计算

空间计算是当前算法最重要的基础能力之一。

程序采用：

**Haversine球面距离公式。**

原因是当前数据采用的是经纬度坐标。

经纬度不能直接使用：

```text
sqrt((x1-x2)²+(y1-y2)²)
```

进行距离计算。

Haversine公式为：

$$
d=
2R
\arcsin
\sqrt{
\sin^2\frac{\Delta\phi}{2}
+
\cos\phi_1
\cos\phi_2
\sin^2\frac{\Delta\lambda}{2}
}
$$

其中：

* (R) 为地球半径；
* (\phi) 为纬度；
* (\lambda) 为经度。

输出结果为两个地理点之间的球面距离。

---

# 十三、当前空间算法不是“一基塔循环60次”

代码实际上采用的是：

**矩阵计算。**

如果当前可用机巢为12个，则一次形成：

$$
17845\times12
$$

的距离矩阵。

可以理解成：

| 杆塔   |  石滩 |   杜市 |   桥东 | …… |
| ---- | --: | ---: | ---: | -: |
| T001 | 5.2 | 12.4 | 18.3 |  … |
| T002 | 5.4 | 12.1 | 18.0 |  … |
| T003 | 5.7 | 11.8 | 17.5 |  … |

这样可以一次得到：

> 每基杆塔到所有当前可用机巢的距离。

目前17845×12的数据规模实际上非常小，NumPy完全可以快速计算。

---

# 十四、为什么不是简单找“最近机巢”

这是当前设计中的核心思想之一。

假设某基杆塔T001距离：

```text
机巢A：4.8 km
机巢B：5.1 km
机巢C：5.6 km
```

如果采用传统方法：

```text
T001永久属于机巢A
```

会产生一个严重问题。

假设机巢A今天：

* 已经有大量巡视任务；
* 无人机正在执行临时任务；
* 无人机故障；
* 机巢维护；
* 天气不适宜。

而机巢B实际上距离只多300米。

那么T001完全可以由B来巡视。

因此当前代码为每基杆塔保留：

```python
candidate_top_k = 3
```

即：

> **Top-3候选机巢。**

例如：

```text
T001：
候选1 = A，4.8 km
候选2 = B，5.1 km
候选3 = C，5.6 km
```

这就为后面的动态调度提供了可能。

```text

所有已安装机巢经度
所有已安装机巢纬度
Top-K参数
```

## 输出

例如：

```text
tower_id = T001

rank  nest     distance
1     A        4.8km
2     B        5.1km
3     C        5.6km
```

因此空间计算模型可以概括为：

$$
Tower
\rightarrow
CandidateNestSet
$$

即：

> 一个杆塔对应一组可选择的机巢。

# 十六、第五部分：为什么还要做负载均衡

即使保留3个候选机巢，也不能简单永远选第1名。

当前代码采用：

$$
Cost_{ij}
=========

Distance_{ij}
+
\lambda Load_j
$$

其中：

* (Distance_{ij})：杆塔i到机巢j的距离；
* (Load_j)：当前机巢已经承担的任务量；
* (\lambda)：负载惩罚系数。

算法选择：

$$
Cost
$$

最小的机巢。

# 十七、用案例解释负载均衡

假设杆塔T001有两个候选机巢。

### 情况一

```text
A机巢距离 = 4.8 km
B机巢距离 = 5.0 km
```

如果：

```text
A已有任务 = 10
B已有任务 = 8
```

那么一般仍然选择A。

因为A距离更近，而且负载差异不大。

---

### 情况二

如果变成：

```text
A已有任务 = 500
B已有任务 = 50
```

虽然A距离少0.2km，但是继续把任务全部分给A显然不合理。

算法就可能把T001分配给B。

因此当前思路不是：

> **距离最短优先。**

而是：

> **距离合理的前提下兼顾机巢资源均衡。**

# 十八、为什么不能只按照“杆塔数量”均衡

当前版本使用任务数量作为简化的负载指标。

但是正式版本需要进一步改进。

例如：

```text
机巢A有100个精细巡视任务
机巢B有100个通道巡视任务
```

虽然两者都是100个任务，但工作量可能完全不一样。

因此正式系统建议把：

```text
Load = 任务数量
```

升级为：

$$
Load_j
======

\sum_i ExpectedDuration_i
$$

也就是：

> **使用预计工作分钟数或预计无人机占用小时数作为负载。**

这样更加符合实际。

# 二十三、第八部分：从“任务”到“架次”

## 任务


例如：

# 二十四、为什么不能“一塔一架次”

假设：

```text
机巢到#31距离5km
#31到#32距离300m
#32到#33距离350m
```

如果一塔一架：

```text

架次2：

架次3：
机巢→#33→机巢
```

会产生大量重复往返。

而合理方式应该是：

```text
机巢
→ #31
→ #32
→ #33
→ 机巢
```

一次完成。

所以当前代码会：

1. 按机巢分组；
2. 按线路分组；
3. 按任务类型分组；
4. 按杆塔号排序；
5. 连续向当前架次中加入杆塔。

# 二十五、当前架次构造算法

代码核心思想可以简单理解为：

```text
当前架次为空

加入#31
↓
计算航程和时间
↓
没有超限
↓
继续加入#32
↓
重新计算
↓
没有超限
↓
加入#33
↓
……
```

当加入某一个杆塔以后超过限制：

```text
则当前架次结束
```

新杆塔放到下一个架次。

这是一个：

> **顺序装箱式的线路任务切分算法。**

# 二十六、案例：架次是如何切出来的

假设某线路有：

```text

#32
#33
#34
#35
#36
```

机巢位于线路附近。

假设计算得到：

### 加入#31

```text
预计时间 = 14分钟
```

可以。

### 加入#32

```text
预计时间 = 19分钟
```

可以。

### 加入#33

```text
预计时间 = 24分钟
```

可以。

### 加入#34

```text
预计时间 = 31分钟
```

可以。

### 加入#35

```text
预计时间 = 36分钟
```

仍然可以。

### 再加入#36

假设：

```text
预计时间 = 40分钟
```

而当前仿真参数为：

```text

安全预留8分钟
```

真正允许规划的时间为：

$$

$$

所以：

```text

```

算法判断不能再加入。

最终形成：


然后：

```text

```

这就是当前程序生成架次的基本原理。

# 二十七、第九部分：航程计算方法

对于一个架次：

```text
机巢
→ T1
→ T2
→ T3
→ 机巢
```

总航程不是：

```text
机巢到最远杆塔 × 2
```

而是：

$$
D=
D(N,T_1)
+
D(T_1,T_2)
+
D(T_2,T_3)
+
D(T_3,N)
$$

其中：

* (N)：机巢；
* (T_i)：杆塔。

这才能比较接近真实飞行路径。

# 二十八、第十部分：时间计算

架次预计时间分成两个部分：

$$
T_{sortie}
==========

T_{flight}
+
T_{service}
$$

---

## 28.1 飞行时间

计算：

$$
T_{flight}
==========

\frac{D}{V}
$$

例如：

```text
航程 = 12km
巡航速度 = 36km/h
```

那么：

$$
12/36
=====

0.333小时
$$

即：

```text
约20分钟
```

---

## 28.2 作业时间

假设架次包含4基精细化巡视杆塔。

当前仿真假设：

```text
精细化每塔3分钟
```

那么：

$$
T_{service}
===========

# 4\times3

12分钟
$$

总时间：

$$
T_{sortie}
==========

# 20+12

32分钟
$$

再和最大允许架次时间进行比较。

# 二十九、为什么必须预留安全时间

假设无人机理论最大续航：

```text
45分钟
```

不能安排：

```text
44分钟任务
```

因为现场还会受到：

* 风速；
* 返航路线变化；
* 悬停时间；
* 定位误差；
* 临时避障；
* 电池性能；
* 温度；

等影响。

所以当前代码采用：

$$
T_{usable}
==========

## T_{max}

T_{reserve}
$$

例如：

$$
45-8=37分钟
$$

也就是说：

> 算法原则上只安排37分钟以内的计划任务。

真正项目中建议进一步从“时间安全余量”升级成：

> **电量安全余量。**

即：

$$
E_{mission}
+
E_{reserve}
\le
E_{available}
$$

# 三十、第十一部分：任务编排模型

所有架次生成以后，还需要回答：

> 今天先执行哪个？

这就是任务编排。

当前代码主要综合考虑：

1. 基础业务优先级；
2. 三类周期任务完成进度；
3. 架次执行效率。

可以表示为：

$$
Score
=====

BasePriority
+
FairnessBonus
+
EfficiencyBonus
$$

系统每次选择：

$$
Score
$$

最高的架次进入计划。

# 三十一、基础业务优先级怎么发挥作用

例如当前同时存在：

```text
任务A：临时任务
任务B：红外测温
任务C：通道巡视
```

基础分：

```text
A = 400
B = 300
C = 200
```

在没有非常特殊约束情况下：

```text
A首先执行
```

完成临时任务之后：

```text
B优先
```

之后再安排普通周期任务。

这对应甲方要求：

> 临时任务 > 红外测温 > 其他巡视任务。

# 三十二、最关键的问题：三类任务如何“同步推进”

这是整个项目向老师和专工讲解时最应该重点说明的一部分。

如果只按照基础优先级：

```text
精细 = 200
仿线 = 200
通道 = 200
```

还是存在一个问题：

假设由于线路条件原因，通道巡视每次完成得比较快。

系统可能一直选择通道任务。

最后出现：

```text
通道完成90%
精细完成20%
仿线完成10%
```

虽然它们基础优先级相同，但实际没有实现同步推进。

因此当前代码加入：

> **任务进度赤字机制。**

---

# 三十三、什么是“进度赤字”

假设当前：

```text
精细化完成率 = 60%
通道巡视完成率 = 70%
仿线飞行完成率 = 20%
```

此时：

```text
最高进度 = 70%
```

那么：

```text
精细赤字 = 70%-60%=10%
通道赤字 = 0%
仿线赤字 = 70%-20%=50%
```

程序通过：

$$
FairnessBonus
=============

W\times ProgressDeficit
$$

给落后任务加分。

假设：

$$
W=80
$$

则：

```text
精细额外分约8
仿线额外分约40
通道额外分0
```

于是：

```text
仿线飞行
```

更容易被下一轮调度选中。

---

# 三十四、案例：为什么这可以实现同步推进

假设当前都有任务：

```text
精细：200分
通道：200分
仿线：200分
```

当前进度：

```text
精细：70%
通道：65%
仿线：20%
```

如果没有进度机制：

```text
三者都是200
```

系统可能因为通道任务比较短而一直选择通道。

加入进度赤字以后：

```text
精细 ≈ 200
通道 ≈ 200+少量补偿
仿线 ≈ 200+大量补偿
```

那么系统会主动增加仿线任务。

等仿线进度从20%提高到：

```text
40%
50%
60%
```

它的额外补偿会逐渐下降。

因此算法不会永远偏向仿线。

可以形象地理解成：

> **谁掉队，系统就适当扶谁一把；追上以后，额外照顾自动减少。**

这就是当前代码实现“同步推进”的基本思想。

# 三十五、为什么不采用“轮流执行一次”这种简单方法

有人可能会问：

> 为什么不规定“精细一个、通道一个、仿线一个”轮流执行？

例如：

```text
精细
→ 通道
→ 仿线
→ 精细
→ 通道
→ 仿线
```

这种方法看起来公平，但实际上不合理。

因为三类任务：

* 单次执行时间不同；
* 杆塔数量不同；
* 航程不同；
* 截止周期不同；
* 空间分布不同。

比如：

```text
精细一个架次40分钟
通道一个架次15分钟
仿线一个架次30分钟
```

如果简单1:1:1轮换，并不是真正的业务均衡。

因此当前采用：

> **完成进度驱动的公平调度。**

比固定轮询更加合理。

# 三十六、路线效率为什么也要进入评分

假设两个任务当前业务优先级和进度完全相同。

### 架次A

```text
预计20分钟
完成5个任务
```

### 架次B

```text
预计40分钟
完成2个任务
```

显然A的执行效率更好。

因此代码计算：

$$
Efficiency
==========

\frac{TaskCount}
{ExpectedMinutes}
$$

即：

> 每分钟预计可以完成多少任务。

在其他条件基本相同时，优先安排效率较高的架次。

这样可以减少：

* 无效航程；
* 无人机空飞；
* 机巢占用时间。

# 三十七、完整任务评分思想

当前版本可以概括为：

$$
Score_i
=======

P_i
+
F_i
+
E_i
$$

其中：

### (P_i)

业务基础优先级。

### (F_i)

任务类型同步推进奖励。

### (E_i)

路线效率奖励。

正式版进一步接入巡视历史以后，可以升级成：

$$
Score_i=
P_i
+w_1U_i
+w_2O_i
+w_3F_i
+w_4E_i
$$

其中：

* (U_i)：任务即将到期的紧迫程度；
* (O_i)：已经超期的惩罚；
* (F_i)：进度公平性；
* (E_i)：执行效率。

# 四十四、第一项：天气动态调整目前还未接入

业务要求是：

> 根据天气动态调整巡视任务。

当前代码暂时没有天气数据输入。

正式版本应该增加：

```text
Weather
├─ nest_id
├─ forecast_time
├─ wind_speed
├─ gust
├─ rainfall
├─ visibility
├─ temperature
└─ warning_level
```

然后计算：

$$
Flyable(nest,t)
$$

例如：

```text
08:00—09:30 可飞
09:30—11:00 不可飞
11:00—15:00 可飞
15:00以后不可飞
```

形成：

> **天气可飞窗口。**

调度只能把任务放到可飞窗口中。

# 四十五、案例：天气变化以后如何调整

原计划：

```text
08:00 精细
09:00 通道
10:00 仿线
11:00 精细
```

如果系统在09:20发现：

```text
10:00—12:00风速超限
```

则不应该把全天计划全部删除重算。

正确方法是：

```text
已经完成的任务：保持不变
正在执行的任务：保持或按安全规则返航
尚未执行的任务：重新编排
```

例如调整为：

```text
08:00 精细   已完成
09:00 通道   执行中

10:00—12:00 暂停

12:10 仿线
13:00 精细
```

这种方法称为：

> **滚动调度 Rolling Horizon Scheduling。**

# 四十七、案例：临时任务如何插队

```text
10:00—10:30 通道
10:45—11:20 精细
11:35—12:05 仿线
```

10:20出现临时任务。

```text
12:25—12:55 仿线
```

# 五十、当前算法可以怎样理解为一个闭环

最终完整系统应该形成：

```text
第一步：
根据周期生成任务

第二步：
计算哪些机巢能够执行

第三步：
计算航程和时间

第六步：
自动下发飞行任务

第七步：
无人机执行并反馈

第八步：
更新任务完成进度

第九步：

```

即：

$$
计划
\rightarrow

\rightarrow
反馈
\rightarrow
重新计划

不断循环。

# 五十一、可以给老师举的一个完整综合案例

下面用一个简化案例说明整个系统。

假设有两个机巢：

```text
机巢A
机巢B
```

有一条线路：

```text
L1
```

包含：

```text
#1
#2
#3
#4
#5
#6
```

---

## 第一步：空间计算

假设：

```text
#1距离A = 4.0km
#1距离B = 5.2km

#2距离A = 4.2km
#2距离B = 5.0km

#3距离A = 4.5km
#3距离B = 4.8km
```

系统不会只保存A。

而是保存：

```text
#1 → A、B
#2 → A、B
#3 → B、A
```

作为候选关系。

---

## 第二步：生成任务

今天存在：

```text
#1 精细巡视
#2 精细巡视
#3 通道巡视
#4 通道巡视
#5 仿线飞行
#6 仿线飞行
```

另外临时新增：

```text
#3 临时巡视
```

---

## 第三步：基础优先级

系统首先得到：

```text
#3临时巡视 = 400
其他普通任务 = 200
```

因此临时任务首先进入计划。

---

## 第四步：架次生成

假设：

```text
A机巢 → #1 → #2 → A机巢
```

预计：

```text
28分钟
```

形成：

```text
精细架次A01
```

另外：

```text
B机巢 → #5 → #6 → B机巢
```

预计：

```text
25分钟
```

形成：

```text
仿线架次B01
```

---

## 第五步：同步推进

假设当前月度完成进度：

```text
精细 = 60%
通道 = 55%
仿线 = 20%
```

虽然三类基础分都是：

```text
200
```

但是仿线落后最严重。

因此算法给：

```text
仿线
```

增加进度补偿。

于是：

```text
仿线架次B01
```

会更早进入执行计划。

---

## 第六步：天气变化

假设A机巢：

```text
13:00以后风速过大
```

B机巢仍然正常。

系统重新查询A负责的任务是否存在：

```text
B机巢候选
```

如果某些杆塔：

```text
A距离5km
B距离6km
```

那么可以转由B执行。

这也正是前面为什么必须保留：

> Top-K候选机巢。

---

## 第七步：任务完成反馈

B执行完仿线以后：

```text
仿线完成率：
20% → 25%
```

下一次重新计算时：

```text
FairnessBonus
```

自动下降。

系统继续在：

```text
精细
仿线
通道
```

之间动态平衡。

这就是整个调度系统的基本闭环。

# 五十二、当前算法的优势

当前方案主要有以下优点。

## 1. 算法逻辑可解释

不是黑盒人工智能。

可以明确解释：

```text
为什么选择这个机巢？
为什么先做这个任务？
为什么这个架次只能放5基塔？
为什么仿线今天安排得更多？
```

这对于电力行业生产系统尤其重要。

---

## 2. 没有把缺失数据“假装成真实数据”

当前缺少：

* 塔型；
* 耐张塔；
* 实际飞行参数；
* 巡视历史；
* 天气；
* 实时机巢状态。

程序没有擅自生成所谓真实值。

这保证模型边界清晰。

---

## 3. 当前算法容易逐渐升级

未来可以逐步把：

```text
固定规则
```

升级为：

```text
真实数据驱动模型
```

而不需要推翻整个架构。

---

# 五十三、当前算法仍然存在的不足

从技术角度，也需要客观说明当前版本的不足。

## 1. 机巢分配目前采用贪心算法

当前算法：

```text
一个任务一个任务分配
```

优点是：

* 简单；
* 快；
* 可解释。

但最终结果受到任务处理顺序影响。

正式版本可以升级为：

```text
Min-Cost Flow
```

或者：

```text
CP-SAT
```

进行全局分配。

---

## 2. Top-K机巢目前主要依据距离

真正可达还应该考虑：

```text
禁飞区
地形
障碍物
电池
天气
航路长度
```

因此正式系统里的：

```text
候选机巢
```

应该升级为：

> **真实飞行可达机巢。**

---

## 3. 当前任务分配之后，如果架次不可行，没有再次重新分配

例如：

```text
T001被分给A
```

后续发现：

```text
A执行这个架次超过航程
```

当前代码可能把该架次标记为：

```text
不可行
```

但不会立即自动尝试：

```text
改由B机巢执行
```

正式版本需要形成反馈：

```text
分配
↓
航程验证
↓
失败
↓
回到候选机巢重新分配
```

---

## 4. 当前不同任务类型没有在同一个架次中合并

目前按照：

```text
nest
+ line
+ task_type
```

分别生成架次。

也就是说：

```text
精细巡视
```

和：

```text
红外测温
```

目前会分成不同架次。

正式系统如果设备能力允许，可以进一步实现：

> 一次飞行同时完成多种任务。

例如同一基耐张塔：

```text
一次到达
同时完成精细拍摄
+
红外测温
```

可以显著减少重复飞行。

---

## 5. 通道巡视和仿线目前仍是简化模型

当前以：

```text
每基塔平均服务时间
```

作为近似。

而真正通道巡视、仿线巡视更加适合按照：

```text
线路长度
```

或者：

```text
连续线路段
```

计算。

正式版应进一步建立：

$$
T_{channel}
===========

\frac{LineLength}{InspectionSpeed}
$$

而不是简单：

```text
杆塔数量 × 每塔时间
```

# 五十八、最终总结

整个项目可以从三个层面理解。

## 第一层：空间计算——解决“谁能干”

根据：

```text
机巢坐标
+
杆塔坐标
```

得到：

```text
哪些机巢可以巡视哪些杆塔。
```

不是简单永久绑定最近机巢，而是建立候选机巢集合。

---

## 第二层：时间和架次计算——解决“一次怎么干”

根据：

```text
线路杆塔顺序
+
飞行距离
+
无人机速度
+
任务作业时间
+
安全余量
```

自动形成：

```text
机巢
→ 多基杆塔
→ 机巢
```

的无人机飞行架次。

---

## 第三层：任务编排——解决“先干什么”

严格遵循：

```text
临时任务
>
红外测温
>
精细化=仿线=通道
```

同时通过任务完成进度补偿机制，保证：

```text
精细
仿线
通道
```

同步推进。

最终再结合：

```text
天气
任务进度
设备状态
临时任务
```

进行滚动重新调度。

因此，整个系统最终形成的是一个：

> **基于GIS空间计算、无人机航程时间计算、多任务优先级优化和动态滚动调度的输电线路无人机智能调度系统。**

它不是简单的“最近机巢+任务排序”，而是一个真正围绕：

> **空间可达性、资源能力、时间约束、业务优先级和任务进度**

综合决策的调度模型。
